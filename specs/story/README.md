# Story cards: the hidden notes and the Future Plan line (2026-10-19)

| File | Tool | What it shows |
| --- | --- | --- |
| `notes_z3.py` | Z3 | Which hidden notes ride on the player's message (`gameMasterPage.ts`). Before the fix (`python3 notes_z3.py`): 4 counterexamples: with the GM switched off the persona and Future Plan notes were gone, on a card with no creation step they never came, and the persona note reached cards that never asked for it. After (`--fixed`, `storyNotesRequest`): 6 of 6 hold, the creation note and a story note never together, none during creation. |
| `plans.dfy` / `plans_window12.dfy` | Dafny | The cards' `status.lua` `dropOldPlans`. The loop over the last 12 messages (`plans_window12.dfy`) fails `DeleteKeepsClean`: a rollback moves the lore pass's window back over a reply the loop never reached. Cleaning every older reply (`plans.dfy`, shipped): 11 verified, no older reply keeps a line, for any scan depth. Tied by each card's `tests/status_test.mjs` (a line 15 messages back). |
| `PlanMerge.als` | Alloy 6 | The line under the per-message chat merge (`ChatMerge.als` `fixed`), desktop and phone on one chat: two devices adding a reply from the same base leave two plan lines (`OnePlanAfterMerge` SAT, a counterexample); the next reply on either device heals it (`HealsOnNextReply` UNSAT). Fixed in the app: the key pass and the lore picker read only the newest reply's line (`loreIndex.ts onlyNewestPlan`), so the lore passes see at most one (`LorePassSeesOne` UNSAT) whatever the stored chat holds. |
| `imagegen_fix0.xml` / `imagegen_fix1.xml` + `imagegen.q` | UPPAAL | The cards' `imagegen.lua` cooldown (600 s), set before a picture is asked for. A redraw or reroll supersedes the first job ("a newer picture was asked for this message"). FIX=0 (old): the next reply is refused a picture although nothing failed (`E<> Next.Blocked && !failed` satisfied). FIX=1 (shipped): not reachable; a real failure still cools down (second query satisfied in both). Tied by each card's `tests/imagegen_test.mjs`. |
| `reroll/PanelReroll.tla` + `PanelReroll_{OLD,ST,BOTH,FIXED}.cfg` | TLC | A reroll or delete of replies and the card's panel (`st_*`) and ledger (`led_*`) writes (`gameMasterPage.ts settlePanel`). OLD (no rollback): `PaidOnce` violated, a rerolled kill pays twice. ST (21380949, `st_*` of the latest reply): `LoggedOnce` violated, a rerolled `event:` stays in the timeline. BOTH (`st_*` + `led_*`, latest reply only): `PaidOnce` violated by a rollback over two replies. FIXED (one snapshot per reply, `$panel_log`, back to before the oldest gone): no error, 256 states; with fewer kept snapshots than the rollback is deep (Cap 2) it fails, so the app keeps 20. Tied by `gameMasterPage.test.ts` ("a rerolled or deleted reply takes its panel writes with it"). |
| `dice/card_new_z3.py` | Z3 | The cards' Module 10 fate die ("1–20 means something new surfaces … Never two new events in a row") and the app's note (`gameMasterPage.ts gameMasterRequest`, "Card fate die: NEW EVENT … overrides a QUIET or BUILD pace"), over 7 requests with rerolls. Before (`python3 card_new_z3.py`): two kept replies in a row told NEW (sat). After (`--fixed`, `cardNewMark`): unsat, and a NEW after a quiet reply is never silenced (unsat); without the reroll mark (`$gm_new_prev`) the second fails. Tied by `gameMasterPage.test.ts` ("never told two replies in a row"). |

Run: `python3 notes_z3.py [--fixed]`; `dafny verify plans.dfy`; `java -jar alloy.jar exec -f -o /tmp/out PlanMerge.als` (brew OpenJDK); `verifyta -q imagegen_fix1.xml imagegen.q`.

The models that had no cfg now have `*_FIXED.cfg` (the code's configuration: holds) and `*_OLD.cfg` (the first version: violated)
in their folders (SaveLoad, SaveQueue, CotStream, GenStatus, MergeSave, SlotGeneration, SettleRace; `SettleRace_WITNESS.cfg`
is violated on purpose: a page that really died is still settled). `../run_all.sh` runs every model with its tool.
